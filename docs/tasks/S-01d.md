# S-01d：调度器

| 字段 | 内容 |
|---|---|
| 任务 ID | S-01d（S-01 拆分的第四步） |
| 优先级 | P0 |
| 状态 | IN REVIEW |
| 依赖 | S-01c（进程入口，已合并）、D-03（交易日历） |

## 范围

- **调度器**（server/app/scheduler.py）：作为 tradingd 的常驻任务运行；调度器自身出错时，tradingd 按崩溃退出。
  - 例行评估：每 15 秒调一次 `core.assess()`。
  - 盘中对账：只在常规交易时段、且不在券商重启窗口内进行。开盘即做第一次，之后每 5 分钟一次 `reconcile(INTRADAY)`。
  - 日终对账：每个交易时段收盘后 10 分钟做一次 `reconcile(END_OF_DAY)`，同一天只做一次。
    tradingd 若在收盘后、日终对账前重启，启动后补做。
  - 交易时段、提前收市、节假日全部取自交易日历，不硬编码时刻。
    测试覆盖了感恩节次日 13:00 ET 提前收市、感恩节、周末。
  - 日历查不到（超出覆盖范围、数据错误）：只评估、不对账，并记 ERROR（失败即关闭）。
  - 对账出错只记日志，下一轮照常；对账发现的差异由对账模块自己 SAFE HALT。
  - 券商每日重启窗口：`BrokerWindow`，取配置里的时区与起止时间，可跨午夜；用 zoneinfo 换算，Windows 与 macOS 一致。
- **当日有效意图跨交易时段作废**（S-01c 移交）：
  - `TradingCalendar.session_day(at)`：盘中归当天；盘前归当天；盘后与非交易日归下一个时段。
  - `TradingCore(session_day=…)`：DAY 意图的生成时段与 tradingd 当前时段不同，一律拒绝。
    日历查不到也拒绝。只对从未签发过的意图检查；已签发的意图重投照常返回原决定（S-01c 第二轮评审 P1-A）。
  - `CoreInputs.session_day` 由装配层注入日历。
- **配置** config/runtime/schedule.toml，解析在 `parse_schedule_settings`，严格校验：
  - 盘中对账间隔不得超过 5 分钟（V4.1；只能调密，不能调疏）；
  - 券商窗口：时区必须是认得的时区名，起点写 HH:MM，时长不超过 120 分钟；
  - 未知键一律拒绝。
- **命令行**：`--schedule` 参数；调度配置错误时 tradingd 拒绝启动（78）。
  生产入口用 NYSE 日历，覆盖未来约 13 个月。

## 测试

- tests/integration/app/test_scheduler.py（14 项，真实 NYSE 日历）：
  - 评估间隔；盘中对账只在时段内、开盘即做、每 5 分钟一次、收盘时刻不算盘中；
  - 日终对账只做一次，重启后补做；提前收市跟日历走；节假日与周末只评估；
  - 日历超出范围时只评估；对账出错不影响下一轮；
  - 券商窗口跨午夜，换算到 UTC 后仍成立，无时区时间被拒；窗口内不做盘中对账；
  - 非法调度参数被拒；`session_day` 对盘前、盘后、周末的归属。
- tests/integration/app/test_tradingd.py：调度器在真实 tradingd 里先评估、再做盘中对账；调度器崩溃时 tradingd 按崩溃退出。
- tests/integration/app/test_cli.py：仓库里的调度配置可加载；10 种错误调度配置被拒；调度配置缺失时 tradingd 拒绝启动。
- tests/integration/risk/test_core.py：前一天生成的 DAY 意图被拒；盘前生成的当日意图照常；
  GTD 意图不受这条约束；日历出错时拒绝。

## 评审记录

safety-reviewer（只读）：REQUEST CHANGES。无 P0，P1 四项，P2 七项。

**P1（均已修复）**
- **P1-1 DAY 意图跨时段作废默认关闭，生产装配也没注入。**
  - 改为 `CoreInputs.session_day` 必填，不提供就装配不出交易核心。
  - 测试：tradingd 装配出来的核心会拒绝前一时段生成的 DAY 意图；字段没有默认值。
- **P1-2 日终对账可能静默漏做。**
  - 只有正常跑完才记为已做；出错时按盘中对账间隔重试，并记 ERROR。
  - 补做改为找"最近一个已到日终时刻、本进程还没做成功的时段"（往回最多 7 天），不再只看当天的 UTC 日期。
  - 测试：日终出错会重试，成功才算；UTC 午夜后重启仍能补做。
- **P1-3 评估间隔、日终延迟没有上限。**
  - 已加上限：`assess_seconds ≤ 15`、`end_of_day_delay_minutes ≤ 60`，只能调严。
- **P1-4 调度器和交易核心可能各用一份日历、一个窗口。**
  - 生产入口改为只建一份 `TimeWiring`：交易日历与券商窗口由调度器和交易核心的数据来源共用。
  - 测试：断言调度器拿到的日历和窗口与之同源。

  - 日历查不到只在状态变化时记日志，不再每秒刷屏；

## 移交 / 剩余风险

- 运行状态机的 `broker_window` 来自 `CoreInputs`（由数据源接入时提供）。接入时必须用同一个 `BrokerWindow`，
  也就是 `Scheduler.in_broker_window`，保证“拒绝新增风险”和“暂停盘中对账”使用同一个窗口。
- 受保护配置里的临时休市 / 提前收市登记（calendar_config）要等 D 组接入后才加载；在那之前，生产调度只用日历库自带的节假日。
- 调度状态（日终对账做过哪天）只保存在内存：tradingd 重启后会把最近一个时段的日终对账再做一次。对账可以重复执行，偏保守。
- 券商窗口在夏令时切换当天按墙钟计算：如果窗口落在 01:00–03:00 ET，春季那天窗口会变短，秋季那天会变长。
  当前配置是 23:45 起 15 分钟，不受影响；以后改窗口时要避开这个时段。
- tzdata 只是 pandas 的传递依赖，Windows 上 zoneinfo 完全靠它。以后改依赖时显式声明。
- 生产日历只覆盖启动后约 13 个月：tradingd 连续运行超过这个时间后，会一直"只评估、不对账"并记 ERROR。
  届时需要重启 tradingd；以后加到期前的提前告警。
- 例行评估排在对账后面串行执行：对账如果卡住，评估也会跟着停。风控门禁每次提交都会重新评估，所以影响有限；
  以后给对账加超时。
- 命令日志写失败是否纳入 SAFE HALT（S-01a-confirm）：本任务未处理，仍为剩余风险。
