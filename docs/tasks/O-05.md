## 目标

V4.1：提交后崩溃重启先查单，不重发。覆盖 G1 故障矩阵场景 6（提交后进程崩溃）、场景 7（断线重连期间状态漂移）
与场景 12（备份恢复后首次启动先对账）的 OMS 部分，并把 O-04 中记录“重启吞掉在途回报”缺口的 xfail 用例转为通过。

## 设计

- `OrderManager.recover()`：启动与每次重连后（`ConnectionEvent` CONNECTED，且上次断线后尚未对账）按账本里每个
  已签发、未结束的订单向券商查单：
  - SUBMITTING（提交途中崩溃或断线）→ SUBMIT_TIMEOUT 转 UNKNOWN，记 `recovered_submitting`，再查证；绝不重发；
  - UNKNOWN → `resolve_unknown`（查无此单仍多轮查证并升级）；
  - 活动 / 撤单中 → 按查单结果补记成交（按 execution_id 去重）并以券商状态推进；
    OMS 为 CANCEL_PENDING 而券商仍挂着订单（撤单请求没到券商，或撤单被拒的回报丢了）→ 补发撤单，记 `cancel_resent`；
    券商查不到这张活动订单或同一 orderRef 下有别的单 → 不擅自改状态，记差异并升级；
  - 未定的改单 → `resolve_amendments`；挂起的撤单 → 确认后补发。
- 挂起的撤单在挂起时写审计 `cancel_parked`；重启后据此（且之后没有 CANCEL_REQUESTED）恢复挂起状态。
- 活动订单对账时核对标的、方向、账户、数量与 permId，并核对券商累计成交与账本有效成交量；对不上、券商查不到、
  同一 orderRef 下有别的单、补发撤单被券商说“订单不存在”、补发撤单遇到保护性止损——一律记差异、升级（SAFE HALT），
  本次对账失败。
- 首次签发前按 orderRef 查一次券商：账本没有签发记录而券商已有这张单（从较早备份恢复）→ 拒绝签发并升级，不重复下单。
- 逐单对账：一张订单对不上只让本次对账失败，不中断其余订单（断线期间的撤单照常补发）。
- 对账期间断线（连接代数变化）→ 本次对账作废；落账前再同步复核一次对账状态与连接代数（不跨 await）。
- UNKNOWN 与未定改单的查单失败在对账内向上抛（strict），对账不算完成；查无此单仍按多轮查证升级、不阻塞其余订单。
- **对账完成之前拒绝新单与改单**（失败即关闭）：`submit_approved_intent` 在未对账时先尝试对账，未连接抛
  BrokerUnavailableError，查单失败记 `reconcile_failed` 并拒绝签发；断线 / 券商重启窗口事件把对账状态清掉。
- 不做：外来成交、持仓与现金对账（R-07）；HALT 的持久化与“恢复后保持 HALT”由 ModeManager 负责（C-04 已测）。

## 移交

- **运维说明**：对账中途断线时，其余订单会很快查单失败；UNKNOWN 订单每次失败各记一轮 miss，连续几次重连失败就会
  升级（on_unresolved）。这是失败即关闭的预期行为，不是误报。
- **R-07 / G-01**：SAFE HALT 处置流程要包含“撤掉事实矛盾的订单”这一人工处置项——对账升级的订单不再自动补发
  它自己挂起的撤单。
- **R-07**：外来成交与持仓、现金的对账（断线期间的外来成交只有持仓对账能发现）；对账差异进入 SAFE HALT。
- **S-01**：tradingd 启动顺序（先 ModeManager 恢复 HALT，再连接券商、`recover()`，再接受意图）。
- **B-05**：IBKR 重连后的查单（reqAllOpenOrders、reqCompletedOrders、reqExecutions）行为核实；reqCompletedOrders
  有保留期，比保留期更早的备份里遗漏的签发查不出来；每张新单签发前多一次查单，IBKR 上的耗时与限流需核实；
  适配器暴露自己的连接代数（OMS 只在处理断线事件时推进代数，适配器层“断开又很快重连”时存在很窄的窗口）。
