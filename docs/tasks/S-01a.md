## 目标

把 ModeManager、OMS、风控、数据门禁、对账、运行状态机与急停串成 tradingd 的“交易核心”：固定的启动顺序、
串行化的意图与命令入口、命令按 request_id 去重、例行任务（回报处理、运行状态评估、对账）。

## 非目标

- 撤保护性止损、紧急平仓执行、采用对账基准这三个人工确认命令经交易核心执行：arch_scan 规定这三个入口只能在
  `server/api` 调用，放宽到 `risk/core.py` 的改动被本机权限系统判为“削弱安全规则”拦下，需 Dylan 本人决定如何授权
  （见“待决”）。在此之前交易核心不提供这三个命令。

## 设计

- **启动顺序**：取券商账户 → `ModeManager.start`（失败直接抛出，tradingd 必须退出；持久化 HALT 不自动恢复）
  → `OMS.recover()` → STARTUP 对账 → 运行状态评估。走完才接受意图与命令。查单未完成时报告如实反映（OMS 拒绝新单）。
- **串行化**：意图、券商回报处理、对账、会下单 / 撤单的命令共用一把锁（首期单账户、单 tradingd）。
- **意图入口**：拒绝 `PROTECTIVE_STOP` 类别与 `PROTECTIVE_STOP_SOURCE` / `EMERGENCY_FLATTEN_SOURCE` 来源的外部意图
  （R-04 / R-05 / R-08 移交）；只接受已校验账户的意图。
- **命令入口**：stop_new_orders、cancel_open_orders、preview_flatten、reconcile、resume。按 request_id 去重
  （先查命令日志，再执行，再记结果）；同一 request_id 换了参数即冲突；被拒的命令（确认不符、门槛不满足）结果也记下，
  重试返回原结果；意外异常不记，允许重试。恢复只走 `RunStateMachine.resume`（R-08 六项门槛），恢复后清空上下文提供者的
  “已报告”记录（R-03 移交）。
- **例行任务**：`handle_events`（回报流，串行）、`assess`（出错时尽量持久化 SAFE HALT）、`reconcile(kind)`
  （盘中先查证尚无结果的改单，R-07 移交）。
- **组件登记**（`config/runtime/health.toml`，普通运行配置）：券商连接、账户同步、实时行情为关键（30 秒）；
  新闻、模型为非关键（5 分钟）。取值按开发方建议，由协调方代 Dylan 确定（2026-10-28）。解析器对缺键、多余键、
  类别不认识、时效不是正整数一律拒绝加载。

## 剩余风险

- 命令“执行后、记录前”崩溃或记录失败：重试会再执行一次。stop / cancel / preview / reconcile 重做无害；resume 重做会得到
  “当前不在 HALT”而记为失败（偏保守）。被拒结果永久重放：条件变了必须换新 request_id（S-01b / apid 落实）。
- 操作者身份完全信任调用方：命令通道只能对 apid 开放并经鉴权，workerd 的 outbox 不得路由到 `command()`（S-01b / S-03 硬性要求）。
- 启动前各组件须先报告健康，否则关键组件按“从未报告”算故障，启动即 SAFE HALT（S-01c 落实启动顺序）。
- asyncio 锁不可重入：S-01c 不得把 OMS 的 `on_unresolved` 等回调接到会再拿核心锁的方法上。
