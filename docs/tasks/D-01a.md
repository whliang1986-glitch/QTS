## 目标

所有数据供应商经同一个 `DataProvider` 接口接入（V4.1 5.3），并都必须通过同一套契约测试；
供应商返回的日线按“原始层（不可变）→ 标准化层”的顺序写进数据湖，manifest 带供应商、拉取时间、哈希与授权条款链接。

## 非目标

- 不实现 IBKR 历史数据适配器（D-01b，需要 TWS）；不做回测供应商适配器（D-08）。
- 不做质量门禁与报告（D-05）：这里只拒绝违反接口契约的返回（标的、来源、范围、重复）。
- 不做公司行动入湖与复权（D-04）、不做 DataJob 回补、限速执行与断点续传（D-02）。

## 接口与不变量

- `DataProvider`（Protocol）：`name`、`capabilities`、`rate_limit`、`list_symbols()`、
  `fetch_bars(symbol, start, end, interval)`、`fetch_corporate_actions(symbols, start, end)`、`fetch_calendar(start, end)`。
  - 日期区间是闭区间 `[start, end]`，按 K 线开始时间的 UTC 日期归属（与 D-06 分区一致）；`start > end` 拒绝。
  - 不支持的能力抛 `UnsupportedCapabilityError`，不返回空结果冒充“没有数据”。未知标的抛 `UnknownSymbolError`。
  - 每根 K 线附带供应商原始记录 `raw`（文本），原样进原始层。
- `ProviderCapabilities` 的授权条款链接必填（manifest 要记录）；`RateLimit` 由 D-02 执行。
- `CorporateActionRecord`（domain）：拆股 / 合股用整数比例，现金分红用 Decimal 每股金额；除权日是严格的 `date`。
- `ingest_bars`：先全部校验再写入，任何一根 K 线违反契约（标的不符、来源不是该供应商、超出请求区间、
  同一开始时间重复）整批拒绝、一个分区都不写。按 UTC 日期分组：
  - 原始层 `raw/<供应商>_bars_<周期>`：每日分区在最新版本基础上替换该标的的行，其他标的原样保留；
  - 标准化层 `normalized/bars_<周期>`：同样合并，lineage 指向当日原始分区的版本；
  - 内容相同幂等（不产生新版本）；供应商修订时写新版本，旧版本保留。
  - 合并以“读最新版本 → 写新版本”完成，同一数据集只能有一个写入者（workerd 的 DataJob，D-02）。

## 验收标准

- [ ] FakeDataProvider 通过 DataProvider 契约测试；IBKR 适配器（D-01b）将复用同一套
- [ ] 入湖后原始层与标准化层都有分区，manifest 带授权条款链接，标准化层 lineage 指向原始分区
- [ ] 重跑幂等；第二个标的合并进同一日分区不丢第一个标的；修订写新版本、旧版本可按绑定读回
- [ ] 契约违反整批拒绝且不写任何分区；供应商异常原样上抛且不写任何分区
- [ ] ruff、mypy（win32 与 linux）、pytest、lint-imports、arch_scan 通过

## 必须覆盖的失败场景

- [ ] 返回别的标的、别的来源、区间外、重复开始时间的 K 线
- [ ] 请求不支持的周期或能力
- [ ] 供应商抛错（不可用）
- [ ] 公司行动记录字段与类型不匹配（拆股缺比例、分红缺金额、比例为 1:1、除权日是 datetime）

## 剩余风险

- 合并后的日分区 manifest 只记录本次拉取时间，保留下来的其他标的行实际来自更早的拉取；
  精确来源可经原始层各版本与 lineage 追溯，按标的记录拉取时间留给 D-04 / D-05。

- 同一数据集单写者约定由 D-02 落实。写入前会复核同日分区的最新版本是否仍是合并时的那一版，
  被改动即拒绝（补了测试）；复核与提交之间仍有极短窗口，跨进程的互斥由 D-02 的 DataJob 锁保证。
- 供应商修订删除的 K 线不会从最新版本删除，依赖 D-05 的连续性检查发现。
- 契约测试只在 FakeDataProvider 上运行过；IBKR（D-01b）尚未验证。
