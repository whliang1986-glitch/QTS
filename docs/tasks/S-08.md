## 目标

按 V4.1 第 5.5 节（3-2-1 原则）做本机备份、校验、恢复与保留，并提供目录形式的异地副本。
恢复到干净机器后，账本进入 SAFE HALT，必须先完成券商对账才允许恢复交易。

## 非目标

- 异地副本的目标位置（云对象存储，或另一地点的设备）待 Dylan 决定（计划书 16 章第 7 项）。这里只实现“复制到另一个目录”，云存储另做适配。
- 定时运行（每日盘后备份、每月演练）接入调度器，与 workerd / guardd 的运维任务一起做。
- 不实现 S-11 运行手册的完整演练记录模板，这里只给出恢复步骤（见 `docs/runbooks/S-08-backup-restore.md`）。

## 涉及的受保护路径

无写入。`config/` 会被备份（只读拷贝）；任何路径段名为 `secrets` 的来源一律拒绝，保证密钥不入备份。

## 接口与不变量

- `create_backup(dest_root, *, databases, directories, lake_manifests, now)`：
  - SQLite 用在线备份接口生成一致快照，快照改回 DELETE 日志模式并做 integrity_check；
  - 目录逐文件拷贝，不跟随符号链接；
  - 行情湖只复制各个 `manifest.json`；
  - 全部文件的 SHA-256 写进 `BACKUP_MANIFEST.json`；
  - 先写进临时目录，完成后改名为正式目录，失败时不留下任何东西；
  - 同一秒的多次备份不会重名。
- `verify_backup`：重算哈希；多文件、缺文件、哈希不符、清单损坏、数据库完整性问题，都按损坏处理。校验时以只读、immutable 方式打开数据库，不在备份目录里生成附带文件。
- `restore_backup(path, target_root)`：先校验；目标必须不存在或为空（干净机器）；恢复后再核对一次哈希。
- `restore_and_halt`（装配层）：恢复之后在账本上写入持久化的 SAFE HALT；写入失败则整个恢复失败。
- `prune_backups(keep)`：只删除名字符合备份格式的目录，最近 keep 份永远保留，keep 至少为 1。
- `copy_offsite`：先校验本机备份；复制到目标的临时目录后再改名；目标处再校验一次；不覆盖同名备份。

## 验收标准

- [ ] 备份时源库正被打开：已提交的数据在，未提交的不在
- [ ] 篡改、多文件、缺文件、清单损坏都能被检出；损坏的备份拒绝恢复
- [ ] 恢复到干净目录后，账本处于 SAFE HALT，降风险通道也关闭，等人工处理
- [ ] 密钥目录不入备份
- [ ] ruff、mypy（win32 与 linux）、pytest、lint-imports、arch_scan 通过

## 必须覆盖的失败场景

- [ ] 数据库不存在、备份项名称不合法、没有数据库、目标非空、备份里没有账本、异地已有同名备份、保留份数为 0

## 计划

- 迁移：无。依赖：无新增（只用标准库 sqlite3、shutil、hashlib）。
- 风险：备份只覆盖本机；异地位置未定之前，只满足 3-2-1 中的“2 份”。
- 回滚：还原本提交。

剩余：
- 来源的祖先路径只拦恰好叫 secrets 的段：配置错误时（例如把 `.secrets` 或 `secrets_old` 下的目录配成来源），密钥可能进入备份。运维配置要把来源固定为几个已知目录；
- 密钥防线只有“路径段含 secret”这一条，`.env`、`*.pem`、`credentials*` 这类文件不在拦截范围内，密钥只能放在 `secrets/`；
- 来源目录内含 secret 字样的普通文件（例如 secretary.md）也会让备份失败，属于失败即关闭；
- 硬链接无法靠路径识别；
- 清理时删掉的较旧损坏备份与正常清理混在一起返回，排查要看日志；
- 进程被杀后残留的 `.staging-*` 目录不会自动清理（里面可能是完整的账本快照），运维任务需定期清理并告警。
