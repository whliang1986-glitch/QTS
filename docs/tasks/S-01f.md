# S-01f：交易日历临时覆盖的加载

| 字段 | 内容 |
|---|---|
| 任务 ID | S-01f |
| 优先级 | P1 |
| 状态 | IN REVIEW |
| 依据 | 协调方决定（Dylan 授权协调方决定）：临时休市 / 提前收市的登记由 tradingd 生产入口在启动时加载，放在普通运行配置 `config/runtime/calendar_overrides.toml`，不进受保护路径，只允许“更严” |

## 范围

- `server/app/__main__.py` 的 `production_time`：启动时读 `--calendar-overrides`，默认是 `config/runtime/calendar_overrides.toml`，叠加到 NYSE 交易日历上。
  - 调度器与交易核心共用这一份日历，沿用 S-01d 评审 P1-4 的同源设计。
  - 默认路径的文件缺失：视为没有登记，并记 WARNING（带绝对路径）。命令行显式指定的路径缺失：拒绝启动（78）。
  - 路径读不了（权限、是目录、BOM 等）：拒绝启动，不当成"没有登记"。
  - 格式或内容有误：拒绝启动（78）。解析沿用 D-03 的 `parse_calendar_overrides`（类型严格、未知字段拒绝、重复日期拒绝）；
    “只能更严”的检查沿用 `TradingCalendar.nyse` 的构造校验：
    - 整天休市只能登记在本来开市的交易日；
    - 提前收市只能早于原收盘、晚于开盘；
    - 不能新增开市日，不能推迟收盘；
    - 同一天不能同时登记两种。
  - 早于日历覆盖范围（启动日前 7 天）的旧登记：忽略并记 WARNING，过期的旧登记不会挡住启动。
  - 晚于覆盖范围（启动日后 400 天）的登记：基本是年份笔误，拒绝启动。
  - 守护进程把校验过的 `--schedule` 与 `--calendar-overrides` 以绝对路径透传给子进程，子进程用的与校验过的是同一份。
  - 登记有误时 supervise、workerd、guardd 也一样拒绝启动（有意为之：整套服务用同一份日历，宁可不起，也不带着错误日历运行）。
- `config/runtime/calendar_overrides.toml`：仓库里提供空模板，含说明和例子。
- 数据层没有改动：`TradingCalendar` 与 `calendar_config` 原样复用。

## 测试

tests/integration/app/test_cli.py：

- 仓库模板能加载且不改变日历；默认文件缺失时等于没有登记（记 WARNING），显式路径缺失时拒绝。
- 整天休市、提前收市都生效，调度器拿到的是同一份日历。
- 10 种放宽或格式错误都被拒：
  - 登记在本就休市的日子（圣诞、周日）；
  - 推迟收盘；早于开盘；
  - 周六“提前收市”（等于新增开市）；
  - 重复日期；带时间的日期；
  - 未知字段 `adhoc_openings`（想新增开市日）；
  - 同一天两种登记；
  - 非法 TOML。
- 覆盖范围外的旧登记被忽略，范围内的照常生效。
- 登记有误时 tradingd 以 78 拒绝启动。

## 剩余风险

- 登记只在启动时加载：交易所盘中临时宣布休市时，改完文件要重启 tradingd 才生效。
  重启前，盘中对账仍按原时段进行；风控照常按行情新鲜度、运行状态等门禁拒绝新增风险。
- 这是普通运行配置，不受钩子保护。它只能把交易时间改短（更严），误登记的后果是少交易，不会多交易。
