## 目标

DataJob 驱动历史回补与每日增量（V4.1 5.3），具备以下能力：
- 按“标的 × 年”分片；
- 限速；
- 断点续传；
- 失败重试，只重试暂时性失败；
- 幂等：同一分片重跑结果相同。

每个分片入湖后都生成质量报告，并给出 DATA 组件的健康结论。

## 非目标

- 不接到 workerd 的调度上：定时触发、阈值的运行配置、健康上报接口留到 workerd 接入真实数据源时一起做（B-03 / D-01b）。
- 不做 IBKR 的历史数据适配器（D-01b）：这里只用 FakeDataProvider。
- 不做公司行动的撤销核对：请求窗口内供应商不再返回的事件仍按 D-04 的语义保留，核对报告留给后续任务。

## 允许修改范围

  `server/data/ingest.py` 只改说明（写明调用方必须持有 `.datajob.lock`）。

无。

## 接口与不变量

- `plan_shards(symbols, start, end)`：按“标的 × 年”切分，顺序固定。
- `DataJob.backfill(job, symbols, start, end, force=False)`：
  - 截止日期截到“已收盘并过了发布延迟”的最近交易日；起始日期晚于这一天即拒绝。
  - 每个分片依次做：限速 → 日线入湖 → 公司行动入湖（供应商支持时）→ 质量报告 → 写检查点。
  - 已完成的分片跳过；`force` 时重跑，入湖同内容幂等，不会产生新版本。
- `DataJob.incremental(job, symbols, day)`：
  - 当日收盘并过了发布延迟之后才拉取；
  - 非交易日什么都不做；
  - 日历不覆盖这一天即拒绝。
- 重试：
  - 只对 `ProviderUnavailableError` 重试，按退避 × 2^(n−1) 指数退避，最多 `max_attempts` 次；
  - 契约违反、数据不合格、湖内冲突直接记为失败，不重试；
  - 意外异常先记为失败，再原样上抛。
- 限速：滑动窗口，任意 `per` 时间内最多 `requests` 次请求；每个分片请求两次（日线一次，公司行动一次）。
- 检查点：
  - 存在 SQLite（WAL、synchronous=FULL）的 `datajob_shards` 表，每个 (job, 分片) 一行；
  - 记录状态、累计尝试次数、时间、说明和质量报告；重开数据库后保留。
- 单写者：运行期间持有 `<lake>/.datajob.lock`，拿不到锁即拒绝运行（D-01a / D-04 的合并依赖它）。
- 质量：
  - 历史分片按分片末日评估新鲜度，避免过去年份的分片永远被判为陈旧；
  - `JobSummary.blocked` 是质量门禁要求不得新增风险的标的；
  - `healthy` 为假表示有失败的分片或被阻断的标的。

## 验收标准

- [ ] 断点续传：失败的分片在供应商恢复后补齐，已完成的分片不重复请求
- [ ] 限速：滑动窗口的等待时间正确
- [ ] 幂等：强制重跑不产生新文件
- [ ] ruff、mypy（win32 与 linux）、pytest、lint-imports、arch_scan 通过

## 必须覆盖的失败场景

- [ ] 暂时性失败：重试后成功；重试耗尽后分片记为失败，之后能续传
- [ ] 契约违反：不重试，一个分区都不写
- [ ] 意外异常：记录后上抛
- [ ] 第二个写入者：拒绝
- [ ] 增量：收盘前拒绝；周末不做；超出日历拒绝
- [ ] 质量问题：标的被阻断，`healthy` 为假

## 计划

- 改动文件：见“允许修改范围”。
- 迁移：新表 `datajob_shards`，`CREATE TABLE IF NOT EXISTS`。
- 风险：每个分片读回全部日线做质量检查，回补全市场时较慢，首期标的只有数十到数百只，可以接受。
- 回滚：还原本提交，数据湖与检查点表保留，不影响其他功能。

## 移交

- **workerd 接入（B-03 / D-01b）**：
  - 收盘后由交易日历驱动调用 `incremental`；
  - 阈值与重试参数放进普通运行配置；
  - `JobSummary.healthy` 作为 DATA 组件健康上报（R-08），只能取自覆盖到最近交易日的增量结果；`blocked` 里的标的不得新增风险；
  - 检查点表放在 meta.db；`JobSummary.repaired` 非空时告警排查。
  - 增量只拉当天的公司行动：供应商晚发布的事件靠定期跑当年回补兜底（与 D-04 的撤销核对一起设计）。
  - `healthy` 为真时仍可能有隔离或缺日（完整性只隔离、连续性只报告），需要看报告；
    历史分片一旦受阻，要用 `force` 重跑才能清除。
- **T-04**：回测前确认相关分片都是 DONE，并用 `lake.snapshot` 绑定版本。
