## 目标

V4.1 7.3：四个独立的急停操作（停止新增、撤销未成交、减少风险、紧急平仓），每次操作写审计；急停持久化，
重启不自动恢复；撤单默认保留保护性止损。同时解决 R-02b 留下的问题：HALT 期间连保护性止损也被拒。

## 非目标

- “减少风险”（第 3 级）：需要预先批准的规则与流动性约束，规则须 Dylan 批准，本任务不实现（DEFERRED）。
- API / 面板按钮与操作者身份核验（S 组）；guardd 的撤单（S 组）；R-06 的止损数量同步。
- 不改任何风控阈值或规则口径（紧急平仓订单照查全部规则，含挂单数与下单频率）。

## 设计

- **1. 停止新增订单**：`EmergencyControls.stop_new_orders` → `ModeManager.halt`（持久化；重启后保持 HALT，恢复只能人工
  经 `resume` 的全部健康检查与对账门槛）。先 HALT 后补写急停审计：操作者为空或审计写入失败都不妨碍 HALT。
- **HALT 下的降风险通道**（engine `_precheck` 的模式门）：HALT 时只放行两类订单，且全部规则照查：
  - OMS 随持仓创建的保护性止损（`PROTECTIVE_STOP` 且来源 `PROTECTIVE_STOP_SOURCE`）；
  - 急停入口生成的紧急平仓（`REDUCE` 且来源 `EMERGENCY_FLATTEN_SOURCE`）。
  改单一律不放行；开仓即使冒用来源也不放行。由 `ModeManager.risk_reducing_allowed()` 决定：本实例须完成启动校验、
  无闩锁；**SAFE HALT（状态不可信）下不放行**——启动被拒、账户类型不一致、账户变更、重连换账户的 HALT 审计带
  `safe=true`，普通 HALT 带 `safe=false`，**缺标记一律按 SAFE HALT**；按账本写入顺序判断“上次人工恢复后是否进过
  SAFE HALT”，重启后仍有效，后续普通 HALT 洗不掉；读账本出错一律不放行。
  新增公开入口 `ModeManager.safe_halt(reason, actor=...)`：**OMS 的 `on_unresolved`、R-07 对账发现的负持仓与外来订单、
  数据门禁的状态不可信都必须接到这里，不能接普通 `halt`**（S-01 / R-07 / R-03 接线时落实）。
- **2. 撤销未成交订单**：逐单撤开仓单与减仓单，保护性止损保留；返回每单结果（被 OMS 拒绝的如 SUBMITTING/UNKNOWN
  单列出原因）；`unconfirmed_cancels()` 列出已发请求但未确认终态的订单（请求发出不算成功）。
  连止损一起撤：`cancel_protective_stops` 须逐字输入 `PROTECTIVE_CANCEL_PHRASE`，走 OMS 新增的唯一入口
  `request_cancel_protective`（只接保护性止损；状态未确认先查证，不撤）。
- **4. 紧急平仓**：`preview_flatten` 列出每个持仓的数量（只取已校验账户的持仓、按标的合计、扣除已挂减仓单，
  向下取整）、保护价、最新价、最大滑点与风险提示，生成确认短语；`emergency_flatten` 须逐字输入该短语，预览 60 秒内有效，
  执行时重新计算，标的、数量、保护价任一与预览不同即拒绝；预览在第一次等待前即被领取，一次只能执行一次；
  执行整段加锁串行，已挂减仓单取券商快照与本地账本的并集（按意图去重），所以连点、并发、两次预览都不会重复卖出。
  **标的还挂着保护性止损（含撤单未确认）时拒绝平仓**：止损触发与平仓限价单同时成交会卖成空头；
  须先经第 2 级二次确认撤止损、等撤单确认，再平仓。负持仓、挂单未知、持仓不属于已校验账户一律拒绝。
  逐行提交、逐行容错，返回每行的风控结果或错误。订单是带保护价的限价减仓单：保护价 = 最新价 ×（1 − 当前生效的 `max_limit_deviation`），
  向上取到最小跳动（不放开市价单）。参数、持仓、最新价、标的规格任一缺失即拒绝（失败即关闭）。
- arch_scan 只收紧：`protective-cancel-entry`（`request_cancel_protective` 只在 oms 与 risk/emergency.py）、
  `emergency-confirm`（`cancel_protective_stops`、`emergency_flatten`、确认短语只在 risk/emergency.py 与 api）、
  `emergency-source`（紧急平仓来源标识及字面量只在 domain 与 risk）。

## 剩余风险 / 后续

- 紧急平仓照查挂单数与频率上限：持仓标的多于“每分钟下单上限”时，超出的行会被拒，需要稍后重新预览执行剩余部分
  （计划会扣除已挂的减仓单）。是否给紧急平仓单独的频率豁免属于风控规则变更，须 Dylan 决定。
- 先撤单再平仓：若开仓挂单很多，挂单数上限可能拒绝平仓单；运行手册应写明先执行第 2 级。
- 账户快照用占位评估对象采集（上下文提供者按账户取数）；R-03 接入真实提供者时须保证不依赖评估对象的标的。
- 操作者身份核验在 S 组 API 鉴权时接上；目前 actor 只校验非空。
- “halt”“resumed”是通用审计动作名，未列入 arch_scan 受保护名（字符串太常见，会误报）；能写账本的只有 tradingd，
  伪造一条 resumed 审计可以洗掉 SAFE HALT 标记。S-01 收紧账本写权限时一并处理（改专有常量并纳入 mode-write）。
- 撤止损后断线：重连时 OMS 对止损的撤单不自动重发而是上报，对账会一直失败到人工处理（失败即关闭）；运行手册须写明。
- `unconfirmed_cancels()` 与预览只在本进程内存里，重启后以 OMS 状态为准，预览须重新生成。
- 紧急平仓依赖 R-06 前不能保证每个持仓都有止损；本任务只保证“有止损就先撤再平”。
- **反向竞态（移交 R-06，硬约束）**：平仓单已挂出后，若撤单未确认的买单成交、OMS 随新持仓建止损，或 R-06 给“无止损持仓”补建止损，
  R-04 规则要求止损数量等于全部持仓、不扣已挂减仓单，止损与平仓单同时成交会卖成空头。目前仓库没有创建止损意图的代码，触发不了；
  R-06 须做到：有在途紧急平仓或减仓单的标的不补建止损，或止损数量 = 持仓 − 未结束减仓卖单（后者改 R-04 规则口径，须 Dylan 批准）。
- **来源冒用（移交 S-01）**：arch_scan 只拦常量名和字面量，拼接出的 `risk.emergency_flatten` 能让外部减仓单在 HALT 下通过模式门
  （仍查全部规则、不能做空）。S-01 的 IPC 入口必须拒绝 strategy_id 等于 `EMERGENCY_FLATTEN_SOURCE` 或 `PROTECTIVE_STOP_SOURCE` 的外部意图。
- **SAFE HALT 尚未接线**：OMS `on_unresolved`、R-07 对账、R-03 数据门禁还没接到 `safe_halt`；接线之前这些状态不可信的情况
  不会自动 HALT。S-01 / R-07 / R-03 各自负责接上并补测试。
- 执行时价格比对口径：标的、数量严格一致；保护价只在低于预览时拒绝（更高照常执行），不比较最新价，避免盘中价格跳动使急停用不了。
- 每次计划会遍历全部历史签发；订单量大以后需要按未结束状态建索引（性能问题，不影响正确性）。
- api 不能直接 import 本模块（间接依赖 broker），S 组须经 IPC 调用。
