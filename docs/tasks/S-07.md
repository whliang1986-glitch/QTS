## 目标

告警有统一入口，按级别分发（V4.1 10.4）：
- P0（重复下单风险、账户状态未知、实盘误切换、急停失效、保护性止损缺失）推送到手机，并重复提醒直到人工确认；
- P1（券商断线、行情严重陈旧、对账不一致）推送到手机一次；
- P2、P3 只进面板与日志。

渠道可换：首个实现是 Telegram（Dylan 2026-11-04 选定）。
外部心跳：服务器定时向外部的“死人开关”服务报平安，服务器断电或断网时由外部服务报警（V4.1 7.x、R14）。

## 非目标

- 不真正联网发送：Dylan 提供 Telegram 机器人之前，开发期只用假发送器测试；真实发送的联调在 F-05 / G4 演练里做。
- 不做面板里的告警页（S-05），也不把告警接进各个检测点（各任务按需调用 `AlertHub.raise_alert`；本任务先接 guardd 的 tradingd 心跳丢失）。
- 告警消息的多语言在 S-12 做。本任务的消息结构按“代码 + 参数”设计，便于以后翻译。

## 接口与不变量

- `Alert(level, code, params, key)`：key 是去重键，同一 key 在未确认期间只算一条告警。
- `AlertChannel` 协议：`send(text)`，失败必须抛出。`TelegramChannel` 的机器人令牌从凭据存储读取（`SensitiveValue`），
  令牌不进日志、异常信息或 URL 日志；chat_id 写在普通配置里。
- `AlertHub`：
  - 所有级别都写结构化日志（第一条通路）；
  - P0、P1 经手机渠道推送（第二条通路）；发送失败按退避重试，并记录在日志里；
  - P0 未确认时每隔 `repeat_every` 重复推送；`acknowledge(key, actor)` 停止重复提醒，但不解除风险状态（V4.1 10.3）；
  - `resolve(key)` 由检测方在风险消失时调用；同一 key 在解除前只算一条（每轮重复上报不推送、不刷日志）；
  - `raise_alert` 只登记，不做网络 I/O；`pump` 在线程里发送（guardd 后台每秒一次，带总时限）；发送有全局限速，防止告警风暴把渠道打爆。
- 外部心跳 `HeartbeatPinger`：定时 GET 一个由配置给出的地址（如 healthchecks.io），失败只记日志，不影响交易。
- 失败即关闭：手机渠道不可用（例如缺凭据）时，告警照常写日志，并在面板与日志里标记“手机通路不可用”；
  交易不因告警通路故障而停止，但 G4 门禁要求通路可用。

## 验收标准

- [ ] 模拟故障（tradingd 心跳丢失）后，1 分钟内假发送器收到推送（用假时钟验证）。
- [ ] P0 在确认前重复提醒，确认后停止；P1 只推一次；P2、P3 不推送。
- [ ] 发送失败会重试，令牌不出现在任何日志里。
- [ ] 同 key 去重；告警风暴时限速。
