## 目标

全系统统一输出单行 JSON 日志，correlation_id 贯穿一次请求或一条订单链，日志与审计事件写出前统一脱敏
（密钥、像密钥的字段、IBKR 账户号）。

## 非目标

- 不做日志采集、轮转策略与告警（运维任务）；不改现有模块的日志调用点（各任务接入时使用本模块）。
- 不选用 structlog：标准库 logging + contextvars 足够，少一个依赖；第三方库日志在创建记录时统一脱敏。

## 允许修改范围

- 可以改：`server/storage/logs.py`（新建）、`tests/unit/test_structured_logs.py`、本任务单；
  `server/risk/mode_manager.py` 与 `tests/integration/risk/test_mode_manager.py`（只改 `mask_account` 的引用，统一遮挡口径，不涉及风控判定）。
- 不得改：受保护路径、其他任务的公共接口。

## 接口与不变量

- `correlation_scope(cid=None)`：给定则沿用，否则沿用外层，外层也没有就新建；基于 contextvars，异步任务之间隔离。
- `configure_logging(target, level)`：让所有 logger 在 makeRecord（合并 extra 之后）就地脱敏，
  第三方库自带的 handler、propagate=False 的 logger 也只拿到脱敏后的记录；再给根 logger 装上
  `RedactingFilter` + `JsonFormatter`（重复调用替换上一次的 handler）。脱敏出错时降级为丢弃内容，不抛异常。
  JSON 字段：`ts`（UTC ISO）、`level`、`logger`、`message`、`correlation_id`、`fields`、`exception`、`stack`；
  Decimal 编码为字符串、时间为 ISO 8601、非有限浮点为字符串（严格 JSON）。
- `log_event(logger, level, event, /, **fields)`：结构化字段（字段名不受限制）。
- 脱敏：`SensitiveValue` → `***`；字段名经 `credentials.is_credential_key` 判定为密钥的值 → `***`；映射的键按文本规则脱敏；
  文本中的 IBKR 账户号（U / F / I / DU / DF / DI + 5–9 位数字，不分大小写）只保留字母前缀与后 3 位；
  异常与调用栈文本同样按文本规则脱敏。C-04 的 `mask_account` 改为引用本模块（口径统一）。
- `correlation_scope` 校验 id（非空、无空白、≤128）。
- `record_audit(repo, action, actor, at, detail, correlation_id)`：actor、action、detail 先脱敏，detail 按严格 JSON 编码，
  写入账本审计表（只追加）；每次生成新 event_id，不是重试幂等入口。

## 已知局限

- 无法识别任意形态的明文密钥：密钥只能以 `SensitiveValue` 存在，不得拼进异常或消息（CLAUDE.md 红线 7）。
- 账户号只按 IBKR 格式识别；其他券商接入时扩充 `ACCOUNT_PATTERN`。
- contextvars 不跨线程：threading.Thread、run_in_executor 与 ib_async 协议回调拿不到调用方的 correlation_id，须显式传递
  （或 `contextvars.copy_context().run`）。
- 自定义 Logger 子类不会被替换为脱敏 logger；它们的记录仍由根 handler 上的过滤器脱敏，但自带 handler 的需另行接入。
- 记录上仍保留原始 `exc_info`：标准 Formatter 使用已脱敏的 `exc_text`，但直接渲染异常对象的 handler
  （rich 的 RichHandler、带 locals 的 traceback、Sentry 类）不得接入。
- `configure_logging` 是进程级设置（logger 类与已有 logger 都换成脱敏版本），测试进程中同样一直生效，这是有意的。
