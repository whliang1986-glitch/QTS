## 目标

网页上能看到告警（未确认、已确认、已解除）并由 owner 确认，能查看 apid 的审计日志。
告警记录在 guardd 重启后不丢；告警库坏了也不漏报。

## 非目标

- 不做告警的手动“解除”：解除只由检测方在风险确实消失时执行（V4.1 10.3）。
- 不做告警规则配置、静音、按级别订阅。
- 不显示 tradingd、guardd 的结构化运行日志（另立任务；这里只有 apid 审计）。
- 确认不改变任何交易状态：不解除 HALT，不撤单，不下单。

## 设计

### 数据放在哪里、谁写谁读

| 库 | 写者 | 读者 | 内容 |
|---|---|---|---|
| `alerts.db`（与 api.db 同目录） | 只有 guardd | apid（`mode=ro`，每次读完即关） | 告警事件：raised / acked / resolved，只追加 |
| `api.db` v2 | 只有 apid | guardd（`mode=ro`，只用 SQL） | 新增 `alert_acks`：网页确认请求，只追加 |

- 一次“发生”是一条 raised 事件，它的 seq 就是告警编号 `alert_id`；确认、解除各追加一条事件引用它，
  每次发生最多各一条（唯一索引）。当前状态由事件推出；UPDATE、DELETE 被触发器拒绝；
  结构版本或触发器不对就拒绝打开。
- api.db 从 v1 升级到 v2 只新增表与触发器，不动已有数据。

### 告警生命周期

1. guardd 的 AlertHub 登记告警时写 raised，确认时写 acked，解除时写 resolved。
2. guardd 启动时从 alerts.db 恢复未解除的告警：未确认的 P0 立即再提醒，其他只恢复状态，不重复推送。
3. alerts.db 打不开或写入失败：报一条 P1 `alert_store_failed`（只在内存里），之后只在内存里继续。
   推送与重复提醒照常，不漏报。代价是网页可能看不到之后的新告警，这条 P1 会推送到手机说明这一点。

### 网页确认

1. owner 点“确认”→ `POST /v1/alerts/{id}/ack`。请求里只有编号；操作者取令牌身份，请求体里的内容一律不用。
2. apid 只读核对：编号不存在返回 404；已解除返回 409；已确认返回 `already: true`，不重复记录。
3. 否则在 api.db 的同一个事务里写确认请求和审计（`alert_ack_requested`）。审计写不进去，确认请求也不落盘，返回 503。
4. guardd 每秒只读查一次新的确认请求，交给 AlertHub。只有当前未解除的那次发生的编号与请求一致才确认。
   旧页面上的确认不会作用于同一问题后来的新发生。重启后从头读也无害（确认是幂等的）。
5. 确认只停止重复提醒，不解除风险。

### 接口

| 接口 | 角色 | 读不了时 |
|---|---|---|
| `GET /v1/alerts?limit=` | owner、viewer | 503“无法获取告警”，不返回空列表 |
| `POST /v1/alerts/{id}/ack` | 只有 owner | 503（写入失败）、404、409 |
| `GET /v1/audit?limit=&before=` | 只有 owner | 503 |

告警的 `text` 同时给中英文，用 guardd 推送时的同一份模板渲染；代码已下线的旧记录原样显示，不丢。

### 网页

- 新增“告警”和“审计日志”两个页面，中英文都有，深浅主题都有，手机上是单列卡片。
- 告警页每 5 秒刷新，默认只看未解除。读不到时显示“无法获取告警”，并提示这不代表没有告警。
- viewer 能看告警，但没有确认按钮；审计日志只有 owner 能看，viewer 看到提示。
- 审计日志从新到旧，满 100 条可以加载更早的记录。

### 评审修复（safety-reviewer 第一轮：REQUEST CHANGES，4 个 P1）

| 问题 | 修法 |
|---|---|
| P1-1 alerts.db 重建后编号从 1 重来，旧确认请求可能误确认新告警 | alerts.db 建库时生成随机库编号 `store_id`；确认请求带上它；guardd 只认库编号相同、且请求时间不早于这次发生的请求 |
| P1-2 “券商断线”告警落盘后永不解除，之后再断线不推送 | guardd 每轮检查成功后解除它；集成测试覆盖“断线 → 重连 → 再断线会再告警” |
| P1-3 告警库目录建不出来时 guardd 崩溃 | `OSError` 也转成告警库错误；装配时任何异常都降级为内存模式并报 P1 |
| P1-4 apid 配置坏了 guardd 拒绝启动 | guardd 读 apid 配置失败只记日志，告警改为只在内存里（报 P1），照常看门 |
| P2-1 只取最近 200 条，旧的未解除告警可能被挤掉 | 返回“全部未解除 + 最近 limit 条” |
| P2-2 告警库降级后网页仍显示旧数据 | guardd 每 5 秒写健康标记 `alerts.status.json`；标记缺失、超过 30 秒未更新或已降级，apid 返回 503“无法获取告警” |
| P2-3 降级后不再恢复 | 文案写明“重启 guardd 后恢复” |
| P2-4/5 事件循环里写库、线程池偏小 | SQLite 等锁上限 0.5 秒；专用线程池 4 个线程 |
| P2-6 恢复时跳过的记录永远未解除 | 恢复时记为已解除；同 key 被新发生取代的旧记录也记为已解除 |
| P2-7 杂项 | 审计记录损坏按 503；已提交未执行的确认不重复记录；api.db v1→v2 升级前自动备份为 `api.db.v1.bak`；补“guardd 退出后 apid 仍能读”的测试 |

注意：guardd 在 B-03（IBKR 适配器）之前拒绝启动，所以在那之前告警页会一直显示“无法获取告警”。
这是如实反映：没有看门狗在运行，就没有可信的告警记录。

## 验收标准

- [x] 告警发生、确认、解除写进 alerts.db；UPDATE、DELETE 被拒绝；结构或触发器不对拒绝打开
- [x] guardd 重启后恢复未解除告警，未确认的 P0 继续提醒
- [x] 告警库坏了或写入失败：报 P1，内存里继续，推送不受影响
- [x] 网页确认只对同一次发生有效；操作者取令牌身份；确认请求与审计同一事务
- [x] 已确认的再确认不重复记录；已解除返回 409；viewer 403
- [x] 读不到告警返回 503，界面显示“无法获取告警”，不显示“没有告警”
- [x] guardd 只用 SQL 只读访问 api.db，不 import server.api
- [x] 审计日志 owner 可看，viewer 403；可翻页
- [x] 中英文、深浅主题、手机布局截图；axe 无障碍检查覆盖新页面

## 必须覆盖的失败场景

- [x] alerts.db 不存在（只读读取不会创建文件）、内容损坏、触发器被删、版本不认识
- [x] api.db 是 v1（guardd 读确认请求时拒绝；apid 打开时原地升级）
- [x] 审计写入失败 → 确认请求回滚，返回 503
- [x] 旧编号的确认请求、编号不存在的确认请求 → 不动作
- [x] guardd 启动时 alerts.db 损坏 → 报 P1，照常看门

## 计划

- 改动文件：见“允许修改范围”。
- 迁移：api.db v1 → v2（只新增表）；alerts.db 新建 v1。
- 风险：guardd 在事件循环里写 alerts.db（单条 INSERT，WAL + synchronous FULL，本地盘毫秒级）；
  写入出错只会降级，不会冲出看门狗主循环。
- 测试：存储、AlertHub 落盘与降级、确认轮询、接口、网页端到端。
- 回滚：回退本任务提交，并把 api.db 换回升级前自动留下的 `api.db.v1.bak`（v1 代码不认 v2 结构，会拒绝启动）。
  alerts.db 与 alerts.status.json 可以直接删掉（只是告警记录；重建后库编号不同，旧确认请求不会作用于新库）。
