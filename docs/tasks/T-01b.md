## 目标

workerd 每轮先在决策窗口里运行一次策略调度，把意图放进 outbox，再照常投递给 tradingd。

## 做了什么

- `server/app/strategy_runner.py`：`StrategyRunner`，分两步。
  1. `prepare(now)` 在线程里运行：读数据湖、算策略，只把意图收集起来，不碰 outbox。
     不在运行窗口内时直接返回，不读任何数据。
  2. `commit(prepared, outbox)` 在 workerd 的事件循环线程里运行：逐条入队。
     outbox 的 SQLite 连接只能在创建它的线程里用，所以 outbox 始终只在一个线程里，也不会和投递并发。
  - **每个交易日只跑一次，并且落盘**：开始计算之前，先把当天日期原子写进状态文件（`meta.db.runner.json`）；写不进去就不运行。
    重启后读到同一天就跳过。状态文件损坏时抛出，不当作“没跑过”而重跑。
    这样，卖单在 4 分钟窗口内成交后，重跑或重启都不会在当天提议买入（T-02 评审记录的问题）。
  - 外部数据（持仓、账户与行情输入、数据门禁、账户 ID）由 `RunnerSources` 注入。
    任何一项出错，或账户 ID 为空，当天放弃，不补跑，不拿缺省值硬跑。
  - 交易日历出错只在出错信息变化时记一次日志，不刷屏。
  - **时间预算**：`check_delivery` 要求“运行窗口 + 计算上限 + 投递间隔”短于意图限龄，否则拒绝启用（T-01 移交）。
  - 默认调度：开盘后 30 分钟决策，运行窗口 4 分钟，回看 400 个日历日（基准策略约需 230 根日线），发布延迟 1 小时，计算上限 30 秒。
- `server/app/strategies.py`：`run_strategies` 的 outbox 参数改为 `IntentSink` 协议（只需要 `enqueue`），行为不变。
- `server/app/workerd.py`：`run_workerd` 新增可选的 `runner` 与 `clock`。
  - 计算在线程里，用 `wait_for` 设上限。超时只记日志：超时的线程碰不到 outbox，晚些返回也不会写入任何东西。
  - 入队失败只记日志，已入队的部分保留。调度的任何错误都不影响投递。
  - 时间预算不够时拒绝启动（退出码 78）。

## 生产接入

生产 workerd 暂时不传 `runner`：持仓、账户、已结算现金、止损记录、实时报价的真实来源，要等账本只读接口与 B-03、B-04 才有。
在那之前策略调度不启用，workerd 只做投递，行为与之前完全相同。接入时只需在 `__main__` 里装配 `RunnerSources`。

## 验收标准

- [x] 窗口外不读数据、不运行；窗口内每个交易日只跑一次；周末与休市不跑
- [x] 重启后同一天不重跑（新实例读同一个状态文件）；状态文件写不进或损坏时不运行
- [x] 账户、持仓读不到或账户 ID 为空时当天放弃，不入队，不补跑
- [x] 端到端：workerd、runner 与真实 outbox，意图确实入队
- [x] 计算超时：当天放弃，慢线程结束后也不写 outbox
- [x] 时间预算不够时拒绝启用（workerd 退出码 78）；调度出错不影响后续轮次与投递
